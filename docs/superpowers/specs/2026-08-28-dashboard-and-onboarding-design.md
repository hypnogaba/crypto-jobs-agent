# Кабінет і онбординг: опис вакансії, подача, перший запуск

Дата: 2026-08-28 · Гілка: `dashboard-onboarding`

## Проблема

На `/dashboard` під кожною з п'яти вакансій стоїть той самий рядок:

> ЧОМУ ТИ це marketing, одна з твоїх сфер, індустрія fintech.

Три окремі дефекти в одному рядку.

1. **Він про людину, а не про вакансію.** Людина вже знає свій профіль. Вона не знає, що це за робота.
2. **Він однаковий на всіх п'яти картках.** `explainLocally()` (`scanner/src/match.ts`) складає текст із профілю, а профіль на всі п'ять вакансій один. Інформації нуль.
3. **Підпис і текст не утворюють речення.** Eyebrow `dash.why` = «Чому ти», далі одразу «це marketing…».

Причина глибша за верстку: **тексту вакансії в системі немає взагалі.** `jobs_cache` тримає лише company, title, location, remote, salary, tags, url. Greenhouse ми смикаємо з `?content=false` (`scanner/src/sources/ats.ts:14`). Писати опис було буквально нема з чого, тому він і виродився в переказ профілю.

Поруч — чотири менші дефекти тієї ж сторінки:

- дві добірки за одну добу мають однаковий заголовок `2026-08-28`, розрізнити їх неможливо;
- єдина дія на картці — голе посилання, схоже на службовий текст;
- стану вакансії немає: не видно, що відкрито, куди подано, що відкинуто;
- нова людина після онбордингу бачить «Перша добірка прийде завтра вранці» і йде.

## Рішення

| # | Питання | Обрано |
|---|---|---|
| 1 | Головний текст картки | Опис **самої вакансії**, витягнутий із тексту оголошення |
| 2 | Чим його робити | Детермінований витяг. **Без моделі** |
| 3 | Доля «чому ти» | Лишається, але як дрібні чіпи під описом |
| 4 | Кнопка «Податися» | Відкриває вакансію і ставить `applied_at` |
| 5 | Структура | Вузька колонка, заголовки добірок із часом |
| 6 | Онбординг | Перша добірка одразу, екран «що далі» |

## 1 · Опис вакансії

### Звідки береться текст

Перевірено на живих API 2026-08-28:

| ATS | Текст у виклику, який сканер **уже** робить | Дія |
|---|---|---|
| Ashby | `descriptionPlain` (+ `department`, `team`, `employmentType`, `workplaceType`) | читаємо, зайвих запитів нуль |
| Lever | `descriptionBodyPlain`, `descriptionPlain`, `lists` | читаємо, зайвих запитів нуль |
| Greenhouse | лише за `?content=true`: відповідь росте ×21 (42 КБ → 910 КБ на 69 вакансій) | **не** вмикаємо на масовому скані |

Тому один самолікувальний шлях замість трьох окремих:

- **На скані.** Якщо джерело віддало текст разом зі списком (Ashby, Lever, частина RSS) — витягуємо опис одразу.
- **На добірці.** Якщо у вибраної вакансії `summary IS NULL` — довантажуємо текст поштучно, лише для тих ≤5 вакансій, що йдуть людині. Greenhouse потрапляє сюди.
- **Не вийшло** — `summary` лишається `NULL`, картка просто без рядка опису. Порожнього місця не буде: заголовок, локація й чіпи на місці.

**Сирий текст оголошення в базу не пишеться ніколи.** Зберігається лише готовий витяг ≤240 символів. Кеш не роздувається.

Опис вакансії однаковий для всіх людей, тому рахується один раз на вакансію й перевикористовується всіма.

### Витяг

`scanner/src/summary.ts`, чиста функція `summarize(text, company)`:

1. **Декодувати HTML-сутності, потім знімати теги.** Порядок принциповий: Greenhouse віддає екранований HTML (`&lt;p&gt;`), і при зворотному порядку теги випливають у видимий текст. Це помилка, спіймана на прототипі.
2. Розбити на абзаци.
3. **Заголовок про роль.** Якщо є рядок `About the Role`, `The Role`, `What you'll do`, `Your Role`, `Responsibilities` — беремо перший змістовний абзац після нього.
4. **Інакше скоринг** абзаців: `+4` за маркери ролі (`you'll`, `we're looking for`, `in this role`, `responsible for`); `−4` за корпоративні (`our mission`, `millions of users`, `we're a dynamic team`, `globally distributed`); `−5` за службові заголовки (`Benefits`, `Compensation`, `Equal Opportunity`); `−6` за абзац, що відкривається назвою компанії з дієсловом-зв'язкою («Ramp is building…»); `−0.5` за кожен абзац углиб.
5. Обрізати по межі речення до 240 символів.

### Виміряна якість

15 вакансій, три різні форми даних:

| Джерело | З описом | Справді про роль | З'їхало в блурб про команду |
|---|---|---|---|
| Ashby · ramp | 5/5 | 4 | 1 |
| Lever · spotify | 5/5 | 4 | 1 |
| Greenhouse · alpaca | 5/5 | 4 | 1 |
| **Разом** | **15/15** | **12** | **3** |

Кожен опис відрізняється від інших. Це головне: замість п'яти однакових рядків — п'ять різних.

### Свідомі поступки

- **Опис завжди англійською**, навіть коли інтерфейс український. Оголошення написані англійською, а перекладати нічим — модель вимкнено за рішенням 2. Назва й компанія на картці й так англійською.
- **Приблизно кожен п'ятий опис** описує команду або компанію, а не саму роль. Це все одно конкретика про цю вакансію, а не переказ профілю.
- Якщо витяг згодом захочеться покращити, `summary_at` дає змогу перерахувати старі рядки за датою.

## 2 · Чіпи збігу

`scoreJob()` уже рахує конкретні причини, але складає їх у рядок і викидає структуру. Розвертаємо.

```ts
export type MatchFact =
  | { k: "sphere";   v: string }   // id зі словника: "operations"
  | { k: "role";     v: string }   // своя назва ролі
  | { k: "industry"; v: string }   // id: "fintech"
  | { k: "place";    v: string }
  | { k: "level" } | { k: "remote" } | { k: "salary" } | { k: "fresh" };
```

`ScoredJob.reasons: string[]` → `ScoredJob.facts: MatchFact[]`. Перевірено: `reasons` не читає ніхто за межами `match.ts`.

Сканер — окремий пакет і навмисно не імпортує `web/src/lib/vocab.ts` (див. коментар у `scanner/src/digest-copy.ts:8`). Тому **контракт — це JSON у базі**: сканер пише ідентифікатори, сайт розкриває їх у назви через `label()` за локаллю. Побічний виграш — зникає давній дефект, де в добірці стояло сире `operations` замість «Операції та проєкти».

Порядок: роль/сфера → індустрія → рівень → віддалено → локація → вилка → свіжа. Максимум 5. Рендер — тихим рядком під описом, дрібним шрифтом, без рамок.

Старі рядки `match_facts` не мають. Backfill неможливий чесно: профіль міг змінитись відтоді. Fallback — показати `why_fits` прозою, але **без** зламаного підпису.

## 3 · Подача і стан

Міграція додає в `sent`: `applied_at`, `hidden_at`.

Кнопка — це `<a href="/apply/{id}" target="_blank">`, а не форма. `web/src/app/apply/[id]/route.ts` перевіряє, що рядок `sent` належить сесії, ставить `applied_at` і робить 302 на `jobs_cache.url`. Адреса береться **з бази за id**, ніколи з параметра — відкритого редиректу немає. Працює без JS.

`apply-button.tsx` — крихітний клієнтський компонент: той самий `<a>` плюс `router.refresh()` на клік, щоб мітка з'явилась одразу. Без JS усе одно працює, просто потрібне перезавантаження.

**Ховер.** Кнопка завжди в DOM, у спокої приглушена, на `:hover`/`:focus-within` картки — повний контраст. `display:none` не використовуємо: інакше кнопка недосяжна з телефона й з клавіатури.

| Стан | Картка |
|---|---|
| Звичайний | назва · локація · зарплата · опис · чіпи · тиха `Податися ↗` і `✕` |
| Наведення | те саме, кнопки в повний контраст |
| Подано | `✓ Подано 28 серп · Скасувати`, опис і чіпи приглушені |
| Приховано | згортається в рядок `Приховано · Повернути` |

На картку також повертається зарплата: `salary_min` є в `jobs_cache`, але `listMatches` її не вибирає.

## 4 · Структура сторінки

`Shell` має `wide?: boolean` — 1024 або 672 пікселі, третього немає. Замінюємо на `width?: "narrow" | "roomy" | "wide"`. Викликачів два: дашборд бере `roomy` (768), `/sources` лишається `wide` (там таблиця).

Заголовок добірки: `Сьогодні, 09:00 · 5 вакансій · 1 подача`, далі `Вчора, 09:00 · …`, далі `24 серпня, 09:00 · …`. Час рахується в `users.timezone`.

Мітки «на твій запит» **не буде**, хоч вона й була в початковому макеті: `delivery_requests.handled_at` прив'язаний до людини, а не до добірки, тож зв'язати позапланову добірку з запитом неможливо. Вигаданих фактів не показуємо — дві добірки за день розрізняє час.

Кнопки «Не те, що треба» / «Ще п'ять» переїжджають у правий край заголовка добірки, щоб було видно: вони про добірку, а не про останню вакансію.

## 5 · Онбординг

`saveProfile` і фінальний крок бота роблять однаковий `INSERT INTO delivery_requests` — **лише якщо `sent` для цієї людини порожня**. Без цієї умови кожне редагування профілю замовляло б позачергову добірку. Таблиця й погодинний розгрібач уже існують (`scanner/src/digest.ts:138`), нової підсистеми не треба.

Порожній дашборд першого запуску:

```
 ✓  Профіль збережено
 ●  Перша добірка — протягом години
 ○  Далі — щодня о 09:00        ← справжній delivery_hour у своїй зоні

 [ Підключити Telegram ]   Змінити профіль
```

Порожній дашборд не-першого запуску (пауза, вичерпаний кеш) лишає теперішній текст.

У боті `readyText` набуває тієї самої форми з трьох кроків. `/start` для новачка отримує **два рядки** контексту перед першим питанням: що це, скільки питань, що безкоштовно. Не більше.

Опис вакансії йде і в Telegram-добірку — той самий дефект однакових рядків є і там.

## 8 · Тести

- `summarize()`: заголовок про роль виграє в корпоративного абзацу; екранований HTML не лишає тегів у тексті; порожній вхід дає `null`, а не порожній рядок; обрізання йде по межі речення.
- `factsFor()`: порядок і межа в 5; невідомий id не валить рендер.
- `dayLabel()`: межа доби у ненульовій зоні; «вчора» проти «сьогодні».
- `/apply/{id}` з чужим `id` не редіректить на вакансію.
- Перша добірка замовляється рівно один раз: повторне збереження профілю нового рядка не створює.

Юніт-тестів **недостатньо**. Зелені тести вже пропускали справжні дефекти парсера DOU, бо перевіряли функцію, а не те, що записалось. Тому додатково, перед тим як вважати роботу зробленою:

1. Прогнати `summarize()` по живих відповідях Ashby, Lever і Greenhouse — не по фікстурах.
2. Після першого скану **прочитати записані рядки** `jobs_cache.summary` і очима перевірити вибірку: чи немає тегів у тексті, чи не порожньо, чи описи різні.
