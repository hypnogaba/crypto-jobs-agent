# Job Search SaaS — Design (Фаза 3, ревізія)

## Контекст і що змінюється відносно попереднього плану

Це ревізія плану Фази 3 (див. `docs/PROJECT-OVERVIEW.md`, `docs/superpowers/specs/2026-07-28-crypto-hiring-agent-mvp-design.md`). Три речі змінюються відносно попереднього стану:

1. **Хостинг.** Попередній план — переписати сайт на PHP під shared-хостинг `hypnosit` — скасовується. `hypnosit` вже підтверджено мертвим для персистентних процесів на двох інших проєктах користувача (`the-ledger`, `tradebot-dashboard`), і переможцем там стали **Cloudflare Workers** (`@opennextjs/cloudflare`), безкоштовний тариф. Той самий шлях застосовується тут — Next.js-код Фази 3 (уже написаний і протестований локально) переноситься на Cloudflare замість переписування на PHP.
2. **Обсяг продукту.** Продукт більше не crypto-only. У користувача є окремий, вже працюючий персональний бот загального пошуку роботи (Python, `job_search.py`) з набагато зрілішим джерельним рушієм (multi-ATS + агрегатори + Getro + discovery), продуманим анти-спам механізмом і сформульованим "productization blueprint" для точно такого ж продукту, який тут описується. Рішення: **генералізуємо продукт до загального пошуку роботи**, портуємо логіку рушія цього бота (а не пишемо з нуля і не переносимо crypto-only Фазу 1).
3. **Джерело X/Twitter.** Фаза 1 цього репо валідувала гіпотезу саме на X-сигналах (6551.io Twitter API). Той самий провайдер у зрілішому боті виявився повністю запейволеним (HTTP 402 на всіх ендпоінтах) і за місяць роботи не дав жодної придатної вакансії навіть коли працював — усі ліди були спамом без живого ATS-посилання. Рішення користувача: **лишаємось на тому самому провайдері (6551), апгрейднутому до платної підписки**, і використовуємо X **лише як lead-шар** (твіт → назва компанії → перевірка через її офіційний ATS → показ тільки з підтвердженим живим лінком), а не як прямий показ вакансії. Ключі підключаються на етапі імплементації, коли будуть у розпорядженні — у цій специфікації X описаний як точка розширення, не частина MVP-збірки.

## 1. Продукт

Людина заходить на сайт, вводить вільним текстом, кого/де шукає ("хочу бути DevRel у web3, remote"), **або** завантажує CV. Відповідає на кілька уточнюючих питань (категорія, remote/onsite+локація, зарплата — опційно). Підключає Telegram. Щодня отримує до 5 підібраних вакансій із поясненням "чому підходить" — сама вирішує, відгукуватись чи ні. Ніякого автоматичного подання заявок. Сайт англійською, автопереклад на базові мови.

## 2. Архітектура

```
┌──────────────────┐     ┌───────────────────────┐     ┌──────────────┐
│  Web (Next.js на   │────▶│  Cloudflare D1          │◀────│  Scan Worker  │
│  Cloudflare Workers │     │  users / profiles /     │     │  + Cron       │
│  через OpenNext)    │     │  jobs_cache / sent /    │     │  Trigger      │
└──────────────────┘     │  sources_state          │     │  (щоденно)    │
                          └───────────────────────┘     └──────┬───────┘
                                     ▲                           │
                                     │                           ▼
                          ┌───────────────────┐      ┌─────────────────────┐
                          │  Match Worker        │      │  Джерела: ATS JSON    │
                          │  (Claude API:         │      │  (Ashby/Greenhouse/   │
                          │  CV-парсинг +         │      │  Lever) + агрегатори   │
                          │  per-user ранжування  │      │  (Arbeitnow/Remotive/ │
                          │  top-5)               │      │  RemoteOK/HN) + Getro │
                          └────────┬──────────────┘      │  ecosystem-борди      │
                                   │                       │  (+ X пізніше)        │
                                   ▼                       └─────────────────────┘
                          ┌───────────────────┐
                          │  Telegram delivery   │
                          │  (прямий HTTPS з      │
                          │  Worker'а)            │
                          └───────────────────┘

i18n: Cloudflare Workers AI (модель перекладу) — статичні UI-рядки, кешуються в D1.
Claude API/Anthropic-токени тут НЕ використовуються — щоб не палити квоту на переклад.
```

**Компоненти:**

- **Web** — Next.js, деплой на Cloudflare Workers через `@opennextjs/cloudflare` (той самий патерн, що в `the-ledger` і `tradebot-dashboard`). Існуючий код Фази 3 (`web/`) — онбординг, дашборд, налаштування доставки — переноситься сюди майже без змін; замінюється лише Prisma/MySQL-шар на D1-клієнт.
- **Scan Worker** — Cloudflare Worker з Cron Trigger, раз на добу. Логіка **портується з Python `job_search.py`** іншого бота користувача **в TypeScript** (не запускаємо Python-рантайм на Workers — обмежений для мережевих викликів такого обсягу; сам скрипт некомплексний, ~223 LOC, портування дешевше за адаптацію рантайму). Пише сирі результати в `jobs_cache` (D1), спільний кеш для всіх юзерів — не перескановує джерела на кожного юзера окремо.
- **Match Worker** — окремий крок (той самий Cron або наступний): для кожного активного юзера бере keyword pre-filter з `jobs_cache` за його профілем → Claude API ранжує top-5 + пише one-line "чому підходить" → пише результат у `sent`, відправляє в Telegram.
- **D1** — нова база, чиста схема з нуля (без міграції старої Prisma/MySQL-схеми з Фази 3).
- **i18n** — Cloudflare Workers AI translation model (не Claude). Перекладає статичний UI заздалегідь, кешує результат у D1. Динамічний контент (описи вакансій, чернетки) лишається англійською в MVP.

## 3. Онбординг (сайт)

1. Landing (EN, автопереклад під locale браузера/перемикач) — одне поле вільного тексту ("хочу бути DevRel у web3, remote") **або** кнопка "завантажити CV".
2. Якщо вільний текст → Claude API розбирає роль/локацію/remote з тексту → кілька уточнюючих питань (категорія, remote/onsite + локація, зарплата — опційно), попередньо заповнені з розбору, юзер підтверджує/редагує.
   Якщо CV → Claude парсить skills/роль/seniority з файлу → ті самі уточнюючі питання, попередньо заповнені.
3. Підключення Telegram (deep-link на бота, підтверджує `chat_id` назад у профіль).
4. Готово. Перший батч — одразу після підключення Telegram (не чекаємо до наступного добового прогону), далі щодня.

## 4. Пошуковий рушій (Scan Worker)

Портується з `job_search.py` іншого бота, з однією суттєвою зміною: **рольовий фільтр (positive/negative keywords) стає per-user, а не глобальним**. У персональному боті фільтр був захардкожений під конкретні вподобання власника (BD/partnerships/community/ops/DevRel) — тут це буде витягуватись із профілю кожного юзера на етапі Match Worker, а не глобального скану.

**Джерела (MVP, без X):**
- ATS JSON API: Ashby, Greenhouse, Lever — по списку компаній (seed зі списку іншого бота, авто-розширюється: нова фірма, що дала фіт → додається до `STANDING COMPANIES`).
- Агрегатори: Arbeitnow, Remotive, RemoteOK, Hacker News "Who is hiring" — приносять компанії поза фіксованим списком.
- Getro ecosystem-борди (продуктивно для crypto/web3 — напр. Solana collection id 858, інші шукати `getro <ecosystem/VC> jobs collection`).
- Discovery-by-role: ротаційні пошукові запити по 4-6 рольових ключових словах на прогін — знайдені нові фірми верифікуються через власний ATS перед додаванням.

**Свідомо НЕ використовується (успадковано з уроків іншого бота):** пряме HTML-скрапінг для board'ів, що зазвичай Cloudflare/JS-gated (unjobs.org, ReliefWeb, fetch.ai) — fallback на web search; заблоковане джерело ніколи не рахується як "0 вакансій".

**Анти-концентрація** (застосовується на етапі Match Worker, per-user, не глобально): geo-clone dedup, максимум 2 ролі/компанія в одному звіті (решта — `+N ще`), company cooldown (компанія, що з'явилась ≥3× за 7 днів, повертається лише для top-tier fit), KPI — кількість **унікальних компаній**, не сирий обсяг.

**Свіжість:** ≤14 днів.

## 5. Reliability — yield-gate watchdog

Найважливіший урок іншого бота: інструкцій "спробуй ще" недостатньо — потрібна механічна перевірка результату, незалежна від основного скану.

- **Ескалаційна драбина всередині скану:** "нічого нового" — заборонений фінальний стан. Якщо кількість унікальних компаній у `jobs_cache` за прогін < 7 — Scan Worker піднімається драбиною: standing ATS → агрегатори → Getro → discovery-by-role на нові фірми → (якщо і це не дало результату) спроба 3-5 нових джерел.
- **Watchdog:** окремий запуск ~3 год після основного скану, рахує унікальні компанії з живими URL за день. <5 → форсує повторний глибший скан і лишає proof-of-work нотатку. Це ловить випадок, коли основний прогін "здався" передчасно.
- **Per-user delivery:** якщо після повного проходу драбини юзер все одно отримав <5 свіжих матчів — надсилається менше з явною нотаткою "сьогодні менше, ми копали глибше" (за патерном O2/O3 іншого бота), а не тиша.
- **Джерело недоступне (paywall/Cloudflare/JS-gated):** позначається `degraded` у `sources_state`; ≥2 дні поспіль → `deprecated`, автозаміна. Ніколи не рахується як "0 вакансій".
- **Живі URL:** кожен URL перевіряється (live-check) перед показом юзеру — мертві лінки руйнують довіру.
- **Telegram недоступний:** непронадісланий запис лишається в `sent` як `pending`, повторна спроба наступного прогону.

## 6. Матчинг

- Keyword pre-filter з профілю юзера звужує `jobs_cache` до шортліста (~30-60 ролей) — щоб не годувати LLM тисячами вакансій.
- Claude API ранжує шортліст проти профілю → top-5, яких немає в `sent` → one-line "чому підходить".
- Один спільний скан на день обслуговує всіх юзерів — дорога частина лише per-user ранжування, не сам скан.

## 7. Дані (Cloudflare D1)

```sql
users(id PK, telegram_chat_id, created_at, status[active|paused], plan[free], locale, send_hour)
profiles(user_id FK, mode[freetext|cv], raw_input TEXT, cv_text TEXT, parsed_json TEXT,
         location TEXT, remote BOOL, category TEXT, salary_min INT NULL, updated_at)
jobs_cache(id PK, url UNIQUE, company, title, location, remote BOOL, category,
           source TEXT, posted_at, fetched_at)
sent(id PK, user_id FK, job_id FK -> jobs_cache, sent_at, why_fits TEXT, status[sent|pending])
sources_state(source_name PK, status[ok|degraded|deprecated], last_ok_at, consecutive_fail_days)
```

## 8. X/Twitter — точка розширення, не частина MVP

Коли платна підписка 6551.io активна: X додається як **lead-шар** усередині Scan Worker — твіт класифікується як hiring-сигнал → назва компанії → перевірка через її офіційний ATS (той самий multi-ATS шар з §4) → показ **тільки** з підтвердженим живим лінком через ATS, ніколи напряму з твіту. Ключі підключаються під час імплементації.

## 9. Тестування

На відміну від Фази 1 (одноразовий валідаційний тест без автотестів) — це продакшн-код, потребує реального покриття:
- Unit-тести: per-user role/keyword фільтр, dedup/анти-концентрація логіка.
- Integration-level smoke-тест на кожен ATS/агрегатор ендпоінт (мокнутий) — ловити дрейф форми відповіді джерела раніше, ніж він зламає прогін.
- Ручна перевірка повного онбординг-флоу в браузері (`npm run dev` / preview-деплой) перед тим, як вважати готовим.

## 10. Явно поза межами цього дизайну

- Email-relay доставка (тільки Telegram у MVP).
- Ліміти на DM хайрінг-менеджеру / GDPR-профілювання HM — неактуально, у цьому дизайні немає прямого DM-аутріча до наймачів, лише показ вакансій юзеру.
- Монетизація / платні тарифи.
- CV-fit score 0-10, автогенерація cover letter, application tracker, company-watch alerts — усе це вже описано в "extension roadmap" іншого бота як не збудоване, лишається кандидатом на наступну фазу.
- Перейменування репозиторію з `crypto-jobs-agent` — косметика, не блокує розробку.
