# Crypto Hiring Agent — MVP Design

## Контекст

Продуктова ідея (повний опис — окремий документ користувача): агент, що знаходить роботу в web3/crypto для кандидата, готує чернетку заявки/DM, видає до п'яти можливостей на день. Перед побудовою повного продукту потрібно перевірити три припущення (сформульовані в оригінальному документі, розділ 9):

1. Чи вистачає релевантних hiring-можливостей на щоденну пачку.
2. Чи людина натисне send на AI-згенерованій чернетці DM.
3. Чи ці канали (X, Discord, борди) реально дають співбесіди.

Ця специфікація фіксує **весь роадмап** (для спільного бачення), але **детальний план і код стосуються лише Фази 1** — решта навмисно не деталізується, щоб не витрачати час на розробку, яка може виявитись непотрібною.

## Роадмап

### Фаза 1 — X-only тест (ця специфікація, старт зараз)
Моніторинг hiring-сигналів тільки в X, чернетки DM у Telegram особисто користувачу. Без сайту, без інших юзерів, без ATS/бордів. Мета — перевірити припущення 1 і 2 за мінімальну ціну (час, без грошей).

### Фаза 2 — розширення джерел (після валідації Фази 1)
Додати ATS API (Greenhouse/Lever/Ashby), крипто-борди (web3.career тощо). Перенести логіку з Claude Code підписки в самостійний Node.js/TypeScript скрипт з власним Anthropic API ключем (оцінка ~$1.5-3/міс при поточному обсязі). Досі один юзер (сам користувач).

**Відкрите питання (навмисно не вирішене зараз):** чи потрібен простий веб-дашборд для перегляду/керування сигналами в Фазі 2, чи Telegram залишається достатнім до Фази 3. Вирішити на початку Фази 2.

### Фаза 3 — повний продукт
Сайт з онбордингом кандидата (CV, GitHub/X нік), щоденна пачка до 5 карток, шляхи подачі (людський/формальний), email-relay, ліміти на відправника й отримувача. Відповідає розділам 4-8 оригінального документа. Тут з'являються інші юзери.

**Відкриті рішення для Фази 3** (з розділу 10 оригінального документа, не блокують Фазу 1):
- Ліміт DM на одного хайрінг-менеджера/тиждень
- Email-relay opt-in vs риза виглядати як бот (розділ 7, 12)
- GDPR-профілювання хайрінг-менеджерів
- Монетизація, дистрибуція, назва

## Фаза 1 — детальний дизайн

### Мета і критерії успіху

Дослівно з розділу 11.4 оригінального документа — три цифри за тиждень роботи:

1. Скільки hiring-твітів було насправді.
2. Скільки чернеток користувач надіслав би без переписування.
3. Скільки відповіли.

### Архітектура

Виконання — заплановане Claude Code завдання (`/schedule`, хмарний cron), що працює в межах квоти Claude Pro/Max підписки. Жодного окремого Anthropic API ключа на цьому етапі. Жодного сайту, бекенду чи бази даних — увесь стан зберігається у файлах проєктної папки.

```
[Claude Code scheduled task, раз на день]
        │
        ▼
[6551.io Twitter API — twitter_search / twitter_watch]
   (список ~200 crypto-акаунтів)
        │
        ▼
[Класифікація твітів: hiring-сигнал чи ні]
   (LLM-класифікація прямо в межах завдання)
        │
        ▼
[Для кожного hiring-твіта: роль, компанія, контакт]
        │
        ▼
[Генерація чернетки DM]
        │
        ▼
[Дедуп проти файлу стану]
        │
        ▼
[Telegram-бот → повідомлення користувачу]
```

### Компоненти

**Список акаунтів.** ~200 crypto-акаунтів (фаундери, протоколи, HR/рекрутери), зібраний автоматично через KOL/follower-інструменти 6551 API на старті завдання. Зберігається у файлі проєкту, щоб не перезбирати щодня.

**Джерело даних.** 6551.io Twitter API (skill `opentwitter`), токен уже підтверджений робочим. Free-план: 80 повідомлень/день, 4 points — при щоденній (не реал-таймовій) перевірці цього достатньо для тесту; якщо ліміт стане вузьким місцем, користувач готовий доплатити за вищий тариф.

**Класифікація і генерація.** Виконується моделлю самого Claude Code завдання (без окремого API-виклику) — LLM визначає, чи твіт є hiring-сигналом, витягує роль/компанію/контакт (якщо явний), генерує чернетку DM.

**Дедуп/стан.** Простий файл (JSON) у `~/Projects/crypto-jobs-agent/`, що містить ID уже оброблених твітів. Завдання читає його на старті, дописує в кінці прогону.

**Вивід.** Telegram-бот (створюється користувачем через `@BotFather`), одне повідомлення на знайдений hiring-твіт: текст твіту, роль/компанія (якщо визначено), готова чернетка DM.

**Частота.** Раз на день (ранковий прогін).

### Обробка помилок

- X API недоступний / rate limit → пропустити прогін, залогувати у файл стану, не падати мовчки (наступного дня спробувати знову).
- Telegram API недоступний → зберегти непронадіслані сповіщення у файл, спробувати відправити наступного прогону.
- Немає нових hiring-твітів → надіслати коротке повідомлення "сьогодні нічого" (як і описано в оригінальному документі, розділ 4.2) — не мовчати без пояснення.

### Тестування

Оскільки це не production-код, а одноразовий валідаційний тест — формальних автотестів не пишемо. Перевірка відбувається через сам факт роботи: чи прогін щодня видає розумний результат, звірений вручну користувачем протягом тижня.

### Поза межами Фази 1 (явно)

- Сайт, реєстрація кандидата, CV-парсинг
- ATS/борди/Discord/Telegram-канали як джерела
- Кілька юзерів
- Email-relay
- Окремий Anthropic API ключ / самостійний скрипт
- Формальні ліміти на отримувача DM (розділ 10) — не актуально при обсязі одного тестового юзера
